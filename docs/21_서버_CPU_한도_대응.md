# 21. 서버 CPU 한도 대응 (Workers 무료 플랜 10ms)

목표: 서버(`english-bite-api`, Cloudflare Workers 무료 플랜)의 모든 요청이 CPU 10ms 안에 끝나게 한다. 유료 플랜 없이 Error 1102를 피한다.

- 기준일: 2026-11-15
- 상태: 2026-11-15 서버 배포(버전 1629be16), 2026-11-26 운영 측정(2.8). CPU는 24ms → 10ms로 줄었지만 한도에 걸쳐 있다. 첫 문제 받기가 7.7초 걸려 앱이 "인터넷 연결" 오류를 냈다. 이 문제를 먼저 고친다(5장). 2026-11-26 코드 수정·테스트 완료(2.9, 5.1), 앱 번들 올림, 서버 배포(버전 ed3da3f2). QR 테스트·검토 요청 대기
- 이 문서는 작업하면서 계속 고친다. 확인한 것(2장), 한 일(4장), 할 일(5장), 아직 모르는 것(6장)을 나눠 적는다.

## 1. 한도 (Cloudflare 공식 문서)

| 항목 | 무료 | 유료 (Workers Paid) |
|------|------|------|
| 요청당 CPU 시간 | 10ms | 기본 30초, 최대 5분 |
| 요청 수 | 하루 100,000 | 월 1,000만 포함 |
| 가격 | 0 | 계정당 월 최소 $5 |
| 시작 시간 (전역 코드 실행) | 1초 | 1초 |
| Worker 크기 (압축 전) | 64MiB | 64MiB |

- 한도를 넘으면 사용자에게 Error 1102 "Worker exceeded resource limits"가 간다.
- 가끔 넘는 것은 봐준다. 문서 표현은 "If your Worker starts hitting the limit consistently, its execution will be terminated"다. 얼마나 자주면 "consistently"인지는 문서에 없다.
- 전역 코드(모듈 최상위)는 시작 시간 1초 한도를 따로 받는다. 시작에 쓴 CPU가 요청 CPU에 들어가는지는 문서에 없다.
- 크기는 압축 전 크기만 센다. 문서 표현은 "There is no compressed size limit"이다. Wrangler가 보여 주는 gzip 크기는 참고용이다. 번들이 클수록 시작 시간이 늘 수 있다.
- 출처: [Workers Limits](https://developers.cloudflare.com/workers/platform/limits/), [Workers Pricing](https://developers.cloudflare.com/workers/platform/pricing/) (2026-11-15 확인)

### 2.4 무거운 곳 (`src/lib/daily.ts`)

- `pickDaily`
  - 은행 전체를 분류로 거른다(`questions.filter`).
  - 거른 문제 전부에 섞기용 값(`rank`, 문자열 해시)을 계산해 Map을 만든다.
  - 안 본 문제를 다시 거른 뒤, 자리(5개)마다 그 목록 전체를 2~4번 훑는다.
- `grantBonus`: 오늘 낸 문제를 뺀 새 배열을 은행 전체로 만든 뒤 `pickDaily`에 넘긴다.
- 서버 `sets.ts`의 나머지 처리는 사용자 기록 수만큼만 돈다. 은행 전체를 훑지 않는다.

- 첫 문제 받기 7.70초: CPU는 10ms라 거의 모두 대기다. 앱은 요청을 보낸 뒤 10초가 지나면 끊고(`src/lib/api.ts` `TIMEOUT_MS`) "인터넷 연결을 확인하고 다시 시도해 주세요"를 보여 준다. 휴대폰에서 서버까지 가는 시간까지 더해져 10초를 넘은 것으로 본다. 사용자는 "문제를 불러오는 중" 화면을 오래 보다가 이 오류를 보고 다시 시도를 눌렀다. 서버는 앱이 끊은 뒤에도 세트를 만들었고, 다시 시도는 0.71초에 끝났다.
- 서버는 직전 며칠 동안 로그인된 요청이 없었다(11-20 확인 요청은 로그인 전에 거절돼 DB를 부르지 않는다). 첫 DB 연결이 느렸을 것으로 추정하지만 확인하지 않았다.
- 같은 종류의 요청도 걸린 시간이 0.11~1.30초로 들쭉날쭉하다. 새 세트를 만들 때는 DB를 4번 차례로 부른다(사용자, 지난 세트, 새 세트 저장, 세트 다시 읽기).
- Supabase 로그는 보지 못했다. 연결된 Supabase MCP 계정에는 운영 프로젝트(`vgxogzjygedbojmseouz`)가 없다("You do not have permission").

### 2.9 남은 CPU를 찾음: `localeCompare` 첫 호출 (2026-11-26, 로컬)

서버 전체 처리(인증 확인, 진행 기록 정리, 문제 고르기, 응답 만들기)를 메모리 DB로 돌려 쟀다. DB 대기가 없어 걸린 시간이 거의 CPU다(이 PC, Node 24, 실제 은행).

| | 새 세트 1일째 | 2일째 | 3일째 이후 |
|---|---|---|---|
| 바꾸기 전 | 3.3~3.6ms | **8.5~9.7ms** | 0.8~1.9ms |
| `localeCompare`를 뺀 뒤 | 3.6~4.0ms | 1.4~2.6ms | 0.7~1.8ms |

- 2일째만 튀었다. 답 기록 유무와 상관없었고, V8 최적화 컴파일러(`--no-opt`, `--no-maglev`)를 꺼도 그대로였다. GC 멈춤은 0.5~1.2ms로 작았다.
- CPU 프로파일 차이(1일 vs 2일)에서 `byDate`(세트를 날짜순으로 정렬, `server/src/sets.ts`)가 7.58ms였다. 날짜를 `localeCompare`로 비교하는데, 처음 부를 때 로캘 정렬 데이터(ICU)를 준비하는 비용으로 본다. 세트가 2개 이상일 때부터 정렬 비교가 일어난다.
- 운영에서는 새 인스턴스마다 첫 정렬이 이 비용을 치른다(추정). 11-26 테스트 사용자는 세트가 여러 개라 첫 `/daily`와 `/bonus`(10ms)에 들어갔을 것이다. 답 요청은 정렬하지 않아 2~7ms였다.
- 고침: 날짜 키(yyyy-mm-dd, 빈 값 '')는 ASCII라 글자 순서 비교(`compareDateKeys`, `src/lib/history.ts`)로 바꿨다. `byDate`와 복습 순서(`reviewPriority`) 두 곳. 임의 날짜 키 20만 쌍에서 `localeCompare`와 비교 결과 부호가 모두 같았다.
- 남은 1일째 3.6~4.0ms는 코드를 처음 실행하는 비용으로 본다(추정). 운영 CPU는 배포 뒤 다시 잰다.

## 7. 참고

- 로컬에서 `npm test`가 모든 파일에서 `TypeError: Cannot read properties of undefined (reading 'config')`로 실패하면 작업 폴더 경로의 드라이브 문자를 본다. `c:\...`(소문자)에서 돌리면 이렇게 실패하고, 같은 코드를 `C:\...`에서 돌리면 통과했다(2026-11-15, vitest 5.0.5, Windows). 코드 문제가 아니다.
- 콘솔 MCP(`apps-in-toss-console`)가 세션에 안 보이면 드라이브 문자를 본다. 처음에는 `~/.claude.json`의 `C:/...daily-english`(대문자) 프로젝트에만 등록돼 있어서 `c:/...`(소문자)로 연 VSCode 세션이 못 읽었다. 2026-11-26에 사용자 범위(`--scope user`, OAuth client ID `mcp-gateway`)로 다시 등록했다. 같은 날 `claude mcp list`에서 ✔ Connected로 나왔다(로그인 토큰이 이미 있음). 도구는 등록 뒤 새로 연 세션부터 보인다. 새 세션에서 로그인을 요구하면 `/mcp`에서 한다.
- 대조·측정 스크립트는 저장소 밖(작업 임시 폴더)에서 esbuild로 묶어 돌렸다. 바꾸기 전 코드는 커밋 de6e9a5의 `src/lib/daily.ts`다.
